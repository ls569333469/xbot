# 高权重账号新增关注发现投研报告

> 状态：技术投研记录，尚未实施。日期：2026-07-31。
>
> 本文总结“高权重账号新增关注 -> 项目身份识别 -> CA 核验 -> GMGN 历史回测”的试验经验。本文不修改业务代码、不部署服务器、不改变 Engine 状态，也不授权任何真实交易。

## 1. 结论

高权重账号的新增关注具有早期项目发现价值，但不能直接作为自动买入信号。

正确定位是异步投研入口：

```text
高权重账号发生 NEW_FOLLOWER
  -> 去重并保存事件快照
  -> 判断被关注账号的身份
  -> 查找并核验项目 CA
  -> GMGN 验证链、Token 和交易可用性
  -> 生成待人工确认的投研结果
  -> 人工确认后按需生成白名单或未发币项目监控
```

不得实现为：

```text
高权重账号关注任意账号 -> 从简介或帖子提取任意地址 -> 立即买入
```

本轮最重要的经验是：**关注信号、发帖喊单信号和既有白名单互动信号是三条不同线路，必须分开配置、统计和授权。**

## 2. 三条线路的业务边界

| 线路 | 已知信息 | 目标 | 是否进入交易热路径 |
|---|---|---|---|
| 新增关注发现 | 只知道高权重账号新关注了谁，通常不知道项目和 CA | 发现项目、创始人或未发币账号 | 否，默认只投研 |
| P20 发帖/喊单匹配 | 已知 Actor、精确词条、链和固定 CA | 将明确内容映射到既有白名单 | 满足独立授权后可以 |
| 生态账号与项目账号互动 | 已知 Actor、项目账号和固定白名单 CA | 监听明确的账号关系事件 | 满足既有白名单授权后可以 |

新增关注发现的目标 CA 是运行时研究出来的；P20 关键词规则和既有互动规则的目标 CA 都必须在配置时已经固定。二者不能复用同一个资金授权语义。

## 5. 收益计算口径

本轮只做历史模拟，不代表实际可获得收益。

```text
t0 = 6551 记录的关注事件时间
entry = GMGN 中 time >= t0 的第一根 1m K 线 open
peak = 从 entry 到核对时刻所有 K 线的最高 high
max_return = peak / entry - 1
current_return = current_price / entry - 1
```

限制：

1. 未扣除滑点、Gas、Price Impact 和 GMGN 手续费。
2. 未加入 6551 推送、研究、人工确认和交易执行延迟。
3. 小市值 Token 的 K 线最高价不等于该价格下存在足够可成交深度。
4. 关注事件可能晚于用户在其他渠道得知项目的时间。
5. 当前价和历史最高收益会随核对时刻变化，文档中的结果只代表上述快照。

## 6. 主要误判来源

### 6.1 KOL 提及其他项目 CA

交易员或 KOL 经常在同一批帖子中分析多个项目。直接提取其帖子中的所有 CA，会把“点评对象”误认为“账号所属项目”。

### 6.2 Wallet 与 Token CA 混淆

EVM 钱包地址与 Token CA 格式相同。只做正则匹配无法区分，必须结合附近文本、GMGN Token 查询和链上合约类型。

### 6.3 旧项目、迁移前 CA 和当前身份混淆

账号历史帖子可能保留旧项目、旧 Symbol 或迁移前地址。必须确认：

- 当前账号身份是否仍与该项目一致；
- 地址是否为当前有效 Token；
- 是否存在官方迁移或弃用声明；
- 关注发生时该 CA 是否已经存在。

### 6.4 创始人账号没有直接写 CA

项目创始人、CEO、产品负责人可能不在简介中写 CA，但其身份仍有较高价值。此时需要从项目官方账号、官方网站和明确的官方发布帖交叉验证，不能因为简介没有 CA 就直接排除。

### 6.5 简称、Symbol 和项目名歧义

`CC/CROW` 一类结果必须同时保存被关注账号、触发时间、原始简介或帖子、链、完整 CA 和身份归属证据。只有 Symbol 或简称的结果不可审计，也不能进入候选交易。

### 6.6 6551 重复事件

本轮 88 条原始记录中有 16 条重复。去重键至少应包含：

```text
source_handle + target_handle + event_type + provider_event_id
```

当 Provider 没有稳定事件 ID 时，再使用规范化账号和时间窗口做幂等保护。不得仅按显示名去重。

## 7. 身份分类标准

每个被关注账号必须先归入以下一种身份：

| 类型 | 说明 | 后续处理 |
|---|---|---|
| `project_official` | 项目官方账号 | 查官方 CA；已发币进入研究，未发币进入项目监控候选 |
| `founder_or_executive` | 创始人、CEO、核心负责人 | 通过项目官方来源交叉验证身份和 CA |
| `core_contributor` | 明确参与项目建设的核心成员 | 只进入研究，不凭个人帖子直接确认 CA |
| `ecosystem_platform` | 链、Launchpad、交易平台官方或负责人 | 作为生态高权重账号，不视为单一项目方 |
| `kol_or_trader` | KOL、交易员、分析师 | 其帖子 CA 属于内容信号，不属于身份 CA |
| `wallet_or_fund` | 钱包、基金、做市或投资实体 | 转入资金流或投资关系研究，不当作 Token 项目 |
| `unknown` | 证据不足 | 保留待确认或到期关闭 |

同一个账号可以拥有多个标签，但只能有一个当前主身份。账号同时是项目创始人和生态 KOL 时，证据必须按具体项目分别保存。

## 8. CA 证据等级

| 等级 | 证据 | 是否进入项目候选 |
|---|---|---|
| A | 项目官方账号或官方网站发布完整 CA，GMGN 可验证 | 是 |
| B | 已核验创始人发布，且项目官方账号或网站可交叉确认 | 是 |
| C | 官方迁移公告给出新旧 CA，身份和迁移关系均可确认 | 是 |
| D | KOL、社区成员或第三方媒体提及 CA | 否，只作为线索 |
| E | 仅从图片、短链、Symbol、钱包或搜索摘要推断 | 否 |

即使达到 A-C，也只能生成投研候选，不能因为证据等级高而自动获得实盘权限。

## 9. 推荐的自动化框架

### 9.1 低成本分层

```text
Layer 0：6551 事件入库、账号规范化、幂等去重
Layer 1：6551 简介和近期原创帖扫描，提取账号身份与地址候选
Layer 2：GMGN 确认 Token、链、Symbol、流动性和创建时间
Layer 3：只有身份或 CA 归属仍不确定时才调用 Grok
Layer 4：人工确认，生成白名单或未发币项目监控
```

Grok 不应对每条关注事件无条件调用。72 个去重账号最终只有 2 个严格确认 CA，先做确定性筛选能显著减少模型成本和等待时间。

### 9.2 两类输出

**已发币项目发现**：

```text
关注发生时 CA 已存在
  -> 保存项目和 CA 证据
  -> GMGN 回测与风险检查
  -> 人工选择是否生成固定 CA 白名单
```

**未发币项目监控**：

```text
身份已确认但当前没有 CA
  -> 保存项目官方账号和核心成员
  -> 监听官方账号发布完整 CA 或 CA_CREATE
  -> CA 出现后重新核验
  -> 不自动附加生态互动关系
```

未发币项目监控不需要预先绑定 CA，也不应在没有 CA 时创建交易授权。

### 9.3 建议数据结构

每条研究任务至少保存：

```text
source_handle
target_handle
follow_event_id
followed_at
target_identity_type
identity_evidence
candidate_chain_id
candidate_contract_address
ca_evidence_level
ca_existed_at_follow
provider_checks
research_status
reviewed_by
reviewed_at
generated_whitelist_id
```

建议状态：

```text
queued -> screening -> needs_review -> confirmed/rejected/expired
```

Provider 超时或额度不足必须进入 `provider_retryable`，不能与业务上的 `rejected` 混为一类。

## 10. 交易安全边界

新增关注发现至少满足以下全部条件，才允许用户手动生成白名单：

1. 被关注账号身份已核验。
2. CA 达到 A-C 级证据。
3. GMGN 返回的链、CA、名称和 Symbol 一致。
4. CA 在关注发生时已经存在；否则转入未发币监控。
5. 地址不是 Wallet、Router、Pair、LP、代理实现或已弃用旧合约。
6. 多 CA 冲突已解决并明确当前有效地址。
7. 用户重新确认资金模板、离场策略和触发线路。
8. 新生成白名单默认关闭实盘，需要独立启用。

关注事件本身永远不能越过现有 Signal、Live Policy、资金限额、Engine Armed 和 GMGN 下单门禁。

## 11. 6551 与 Grok 成本判断

### 11.1 6551

- 同一个高权重账号只创建一个 6551 Watch。
- 开启新增关注事件后，新增成本主要来自真实事件推送，不按候选 CA 数量创建 Watch。
- 研究结果中的项目账号只有在进入持续监控时才可能新增 Watch。
- 所有去重和 CA 匹配都在 XBOT 本地完成，不增加关键词级 Watch。

### 11.2 Grok

Grok 只处理以下情况：

- 简介没有明确项目身份，但存在项目线索；
- 创始人和项目官方账号需要关系核验；
- 多个 CA 或迁移关系无法由确定性来源解决；
- 需要从公开 X 内容补充身份说明和证据摘要。

Grok 输出必须包含来源、时间和置信度；没有可验证来源的结论只能标记为 `needs_review`。

## 12. 产品交互建议

建议在 KOL 页面增加独立的“新增关注投研”视图，而不是把结果直接塞入白名单：

| 区域 | 内容 |
|---|---|
| 左侧账号筛选 | 高权重来源账号、生态标签、时间范围 |
| 中部任务列表 | 被关注账号、身份、状态、发现时间、CA 数量 |
| 右侧证据面板 | 原始关注事件、简介快照、官方帖子、GMGN 信息、冲突原因 |
| 底部操作 | 确认为项目、转未发币监控、生成白名单、排除 |

每个结果应明确显示：

- “为什么进入候选”；
- “为什么被排除”；
- CA 是从哪里获得的；
- CA 在关注发生时是否已经存在；
- 当前只是投研结果，还是已经生成白名单。

## 13. 与下一轮发帖/喊单测试的衔接

下一轮测试是独立研究，不复用本轮两个 CA 作为全部内容结论：

```text
高权重账号原创发帖
  -> 提取 Cashtag、Hashtag、精确关键词和完整 CA
  -> 区分明确看多、持仓声明、普通讨论、比较引用、负面观点和新闻转述
  -> 将明确目标映射到唯一 chain_id + CA
  -> 以发帖时间为 t0 做 GMGN 历史回测
  -> 评估可用词条、误报率、收益和延迟
```

首轮建议使用 `@theunipcs`，因为其内容中同时存在：

- 高频明确看多：`$USELESS`、`$PONS`；
- 对比引用：`$DOGE`、`$SHIB`；
- 生态叙事和普通项目提及；
- Cashtag、项目账号 Mention 和自然语言混合文本。

这组数据适合验证“出现 Symbol 不等于喊单”“比较对象不能触发交易”和“同一项目重复发帖如何去重”。

## 14. 下一轮测试输出标准

发帖/喊单测试至少输出：

1. 拉取时间范围、原始帖子数和去重帖子数。
2. 每个代币首次出现、首次明确看多和重复看多时间。
3. 命中方式：Cashtag、Hashtag、关键词或完整 CA。
4. 意图分类及对应原文证据。
5. 唯一链和 CA；无法唯一映射时必须拒绝。
6. 发帖后 `1m/5m/15m/1h/6h/24h` 收益和后续最高收益。
7. 扣除执行延迟前后的差异。
8. 同一 Token 重复信号的冷却和去重结果。
9. 只记录、模拟和实盘候选必须分栏展示。

在完成这些数据前，不应根据少量肉眼样本设定自动交易阈值。

## 15. 当前决策

1. 保留高权重账号新增关注投研方向。
2. 默认只做异步研究，不自动买入。
3. 先用确定性规则筛选，再按需调用 Grok。
4. 项目身份和 CA 归属必须分别核验。
5. 已发币项目与未发币项目分流处理。
6. 本轮两个确认 CA 只作为方法验证样本，不作为胜率证明。
7. 下一步独立测试 `@theunipcs` 的发帖/喊单内容，并按 P20 的精确映射原则评估规则。
